# Rust 1.75.0 compatibility guide

This guide applies to the v0.9.0 source tree. Rust **1.75.0** compatibility is an
intentional goal for the published `opencc-jieba-rs` library. Use the repository's
lockfile when reproducing its tested dependency graph. Older releases can have a
different dependency graph and may need their own release-specific guidance.

## What changed in v0.9.0

Jieba is now vendored inside this crate. Embedded dictionaries and models use the
private pure Rust Zstandard decoder; the external `jieba-rs`, `include-flate`,
`libflate`, and `core2` crates are absent from the current dependency graph.
The previous `include-flate` / `libflate` version pins and Git patch for `core2`
are no longer part of this project's setup.

An application may still bring those crates in through another dependency. If an
existing application retains the old workaround, inspect its complete dependency
graph before removing the patch; the current `opencc-jieba-rs` graph does not need it.

Fx hashing is also vendored. `HMM tables` are generated by the root Rust build script
from the bundled model, without an external Jieba macro crate.

## Reproduce a library build

Install and select the toolchain explicitly; the repository no longer tracks a
local Rust toolchain override:

```sh
rustup toolchain install 1.75.0
cargo +1.75.0 --version
rustc +1.75.0 --version
cargo +1.75.0 build --locked -p opencc-jieba-rs
```

From a checkout, exercise the supported library feature combinations with:

```sh
cargo +1.75.0 test --locked -p opencc-jieba-rs
cargo +1.75.0 test --locked -p opencc-jieba-rs --no-default-features
cargo +1.75.0 test --locked -p opencc-jieba-rs --all-features
```

`--locked` prevents Cargo from changing the dependency resolution. It does not
supply missing dependency downloads. Add `--offline` only when the required crates
are already cached. Run these commands from the repository root.

## Features and native build tools

| Configuration           | Available functionality                                                                                | Native Zstandard build required? |
|-------------------------|--------------------------------------------------------------------------------------------------------|----------------------------------|
| Default (`keywords`)    | Conversion, segmentation, POS tagging, normalization, DeTofu, custom-pack loading, TF-IDF and TextRank | No                               |
| `--no-default-features` | The same runtime APIs except keyword extraction and its result/filter types                            | No                               |
| `--all-features`        | Runtime APIs plus `dictionary_build` pack-generation utilities                                         | Yes, for compression             |

Runtime dictionary decoding needs no native Zstandard library or C compiler for
Zstandard. Normal target linker/platform tools are still required. Enabling
`dictionary-build` adds the native `zstd` / `zstd-sys` compression dependency and
its build-tool requirements. It is unnecessary for loading a custom compressed pack.
Pack generation also requires the repository's plaintext `./dicts` source files,
which are not included in the published library archive.

The C API explicitly enables `keywords` to retain its exported functions. Cargo
features are additive: a dependency enabling `keywords` can enable it even if your
own dependency declaration sets `default-features = false`.

## Dependency resolution for downstream applications

The library directly pins `rayon` to **1.10.0** and `rayon-core` to **1.12.1** for
Rust 1.75 compatibility. No additional downstream Rayon pin is needed for this
library. Other dependency requirements permit compatible updates, so a future
fresh resolution can differ from the graph tested in this repository.

Applications should retain their own `Cargo.lock` and verify it with Rust 1.75.0.
The repository's lockfile does not control a downstream application's dependency
resolution. Library maintainers should test dependency updates on the MSRV before
committing a new lockfile.

If an existing application fails to build, inspect the package and dependency path
reported by Cargo rather than restoring the obsolete `core2` patch:

```sh
cargo +1.75.0 tree -p opencc-jieba-rs
cargo +1.75.0 tree -e features -p opencc-jieba-rs
```

For a specific failing dependency, use `cargo +1.75.0 tree -i <crate-name>` from
the application workspace. Check whether the failure is a compiler requirement,
manifest/lockfile format, unavailable dependency download, or missing native tool.
If a compatible dependency version is needed, resolve that package deliberately
and retest; there is no blanket pin or patch list for unrelated application graphs.
A lockfile rewritten by newer Cargo may also use a format older Cargo cannot read;
keep the lockfile compatible with the oldest toolchain you support.

## Repository checks and policy scope

The [Build and Test workflow](.github/workflows/rust_build_test.yml) installs Rust
1.75.0 and tests the locked workspace with all features. Push runs cover libraries,
binaries, integration tests, and examples; pull-request and manual runs also include
doctests. A separate stable-toolchain job checks public docs, operation without
keyword extraction, and published-package integrity.

For the same full workspace check locally:

```sh
cargo +1.75.0 test --locked --workspace --all-features
```

The MSRV policy applies to the published Rust library. The current workspace is
also exercised on Rust 1.75 by CI, but companion applications and external front-ends
have their own platform and toolchain requirements. Compiler compatibility does not
establish compatibility with every operating system or target. In particular, the
Windows 7 release scripts use nightly Rust with `-Z build-std`; they are a separate
build path from the Rust 1.75 library checks.

An MSRV increase should be an intentional, documented release decision. Retest the
library, feature combinations, documentation, and packaged sources when changing
vendored code or dependencies. See the [README release integrity checks](README.md#release-integrity-checks)
for the broader release checklist.
